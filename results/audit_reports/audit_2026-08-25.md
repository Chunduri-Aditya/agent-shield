# Engineering audit — 2026-08-25

Scope: repo engineering health (CI, lint, type coverage, dependency/secret
tooling), not the eval-module roadmap already tracked in
`AGENT_SHIELD_TODO.md` and `BACKLOG.md`. Triggered by a request to audit the
project using Ruflo/Claude-Flow tooling, then plan improvements.

Every claim below was run, not inferred. Commands and exact output are
included so the numbers can't outlive the run that produced them, per this
repo's own verification discipline.

## 0. Ruflo/Claude-Flow tooling verdict: do not use for security scanning

The `ruflo-security-audit:audit` skill shells out to
`npx @claude-flow/cli@latest security scan/cve/threats`. All three
subcommands were tested against this repo and are unfit for use here:

- **`security scan`** returned `No security issues found!` (0/0/0/0) against
  every one of `agent_shield/ evals/ inputs/ tools/ psych/ memory/ exfil/
  drift/ defenses/ tests/ scripts/`, at both `standard` and `deep` depth.
  Verified as a non-functional stub: a canary file containing a hardcoded AWS
  key, a hardcoded Anthropic key, `os.system(cmd)`, `subprocess.call(cmd,
  shell=True)`, and `eval(cmd)` also scored 0/0/0/0. `--output json` silently
  ignored the flag and printed the same text table. Treat this subcommand as
  inert.
- **`security cve --list`** reported "No known vulnerabilities" but its
  stated source is `npm audit --json` — this is a Python project with no
  `package.json`. The result is not evidence of anything.
- **`security threats --model stride`** is the one subcommand that appears to
  read file contents (it errors on a nonexistent path, unlike `scan`). It
  produced exactly one finding: `.env.example` flagged CRITICAL / Info
  Disclosure, "`.env` file tracked in git — secrets may be exposed." This is
  very likely a filename-pattern false positive: `git ls-files` confirms only
  `.env.example` (the template) is tracked and `.env` (real secrets) is
  gitignored, which is the intended, documented convention (see README
  Quickstart: "`.env` is gitignored — add your keys directly"). This finding
  needs a manual eyeball on `.env.example`'s actual contents to close out —
  this session's own sandbox blocks reading any dotenv-pattern file, so it
  could not be verified either way here.

**Recommendation:** don't route security scanning through Ruflo/Claude-Flow's
bundled `security` subcommands again. If automated scanning is wanted, use
tools that actually understand this stack (§3).

## 1. CI has been red since at least 2026-08-08 (5+ consecutive pushes)

```
$ gh run list --limit 5
completed  failure  Document the DPO/LoRA spike in README                            CI  main  2026-08-25T06:45:58Z
completed  failure  Record the DPO/LoRA spike in BACKLOG.md                          CI  main  2026-08-25T06:42:14Z

completed  failure  Anchor tools/ agentic run at n=20 and expand benign fixture corpus  CI  main  2026-08-08T05:50:26Z
```

Root cause, confirmed identical across the oldest (2026-08-08) and newest
(2026-08-25) failing runs via `gh run view --log`: the `Run Ruff` step exits 1
with the same 9 errors both times. Reproduced locally:

```
$ uv run ruff check .
... (9 errors)
Found 9 errors.
[*] 5 fixable with the `--fix` option.
```

The 9: two `RUF002` ambiguous-character docstrings (en dash, multiplication
sign), two `UP035` (`typing.Iterator` → `collections.abc.Iterator`), one
`F401` unused import, one `RUF043` unescaped regex metacharacters in a
`pytest.raises(match=...)`, two `I001` unsorted import blocks. 5 of 9 are
`ruff check --fix` one-liners; the other 4 are single-line manual edits.

This has been invisible for 17 days because local work runs `make test` /
`make eval-*` directly and nobody checked `gh run list`. It's the project's
own "a rule nothing checks is violated silently" pattern, applied to the
build itself.

## 2. `make lint`'s mypy half isn't in CI, and currently fails

`.github/workflows/ci.yml` runs `uv run pytest` and `uv run ruff check .`
only. It never runs `mypy`, even though `Makefile`'s `lint` target is
`ruff check . && mypy`. Running the real target locally:

```
$ uv run mypy
Found 130 errors in 13 files (checked 53 source files)
$ echo $?
1
```

Errors land in real product code, not just tests:
`agent_shield/runtime/proof_metrics.py`, `agent_shield/tr_holdout.py`,
`agent_shield/external_corpus/dedupe.py`, plus `evals/exfil.py` and 8 test
files. This has been accumulating with no gate to catch it.

## 3. mypy's `files` list excludes the shipped runtime perimeter

```
[tool.mypy]
strict = true
files = ["evals", "inputs", "tools", "memory", "main.py", "tests"]
exclude = "(...|^agent_shield/targets/)"
```

`agent_shield/` (the package that ships `agent-shield-guard`,
`agent-shield-mcp-proxy`, `agent-shield-proof` — the README's "Local runtime
perimeter", i.e. the actual product surface) is not in `files` at all, so
mypy strict mode doesn't check it as a first-class target. Same gap for
`psych/`, `exfil/`, `drift/`, `defenses/`, `scripts/`, `report_generator.py`,
`risk_registry.py` — typed coverage exists for `inputs/tools/memory` but not
their siblings. `agent_shield/targets/*` is correctly excluded (imports a
sibling project that isn't a dependency) — that one's deliberate, not a gap.

## 4. No dependency or secret scanning anywhere

Confirmed absent: `.github/dependabot.yml`, `.pre-commit-config.yaml`,
`bandit`, `pip-audit`, `semgrep`, `gitleaks`, `detect-secrets` (grepped repo-
wide). The only attribution guard is the hand-installed `.git/hooks/commit-msg`
documented in `CLAUDE.md`, which already self-documents the friction of
requiring manual reinstall per clone. For a repo that ships a screener whose
entire job is catching hardcoded secrets and unsafe patterns in *other*
people's agents, it currently runs none of that tooling on itself.

## Verified clean / ruled out (don't re-check these)

- `pytest`: 415 passed, exit 0. Test suite itself is healthy.
- No genuine `eval(`/`os.system`/`subprocess(shell=True)`/`pickle.load` in
  real source — the only `eval(` hits are PyTorch's `.eval()` mode calls in
  the DPO/LoRA spike scripts, which is correct usage, not a vulnerability.
- Every `agent_shield` module, including every file under `runtime/`, has at
  least one test file that imports and exercises it — coverage breadth is
  not a gap (checked before claiming one; see verification discipline in
